# HLTV 双库与 Playbook 方向设计（2026-04-24）

## 背景

当前项目已经具备 `HLTV 页面抓取 -> 本地缓存资料库 -> 下载 demo -> 进入解析/回放` 的基础链路，但当前实现仍然是“抓到 recent matches 后直接写本地 cache”，并没有把“素材暂存”和“正式沉淀”分成两层。

同时，项目长期目标不只是比赛浏览和 demo 解析，还需要逐步建立一套围绕战术、投掷物、职业选手与个人收藏内容的 `Playbook` 能力，并与本地 Obsidian 的 Markdown 体系打通。

这份文档用于把当前讨论收敛成统一方向，供后续拆计划和实现时使用。

---

## 2026-04-26 短期执行校准

根据当前短期目标，本轮先不强行拆出完整 `暂存库 / 永久库` 双表结构，而是把现有本地 HLTV cache 校准成“长期缓存库 + 人工加入本地游戏库”的最小闭环：

- `HLTV 搜索 / 获取比赛`：从 HLTV 搜索入口拿到比赛候选，并复用现有 browse 列表展示。
- `星级 gate`：解析 `hltvStarRating`，只有两星及以上比赛才写入本地 cache。
- `长期缓存库`：cache 默认永久保留，不做自动过期；只提供人工确认后的“清除全部”。
- `加入本地游戏库`：用户在本地缓存库中逐场选择比赛，写入 `addedToGameLibraryAt` 状态；这个动作不自动下载 demo。
- `战术部 / Playbook`：本轮只保留为后续关联方向，后续可从“本地游戏库比赛 -> demo / 地图 / 队伍 / 选手 -> Playbook 条目”继续展开。

这意味着，本文下方的“双库”仍作为中长期方向保留；当前实现优先完成可用闭环，避免在 HLTV 搜索、星级 gate、缓存清空、人工加入动作尚未稳定前过早扩大 schema。

---

## 一、HLTV 页面与双库方向

### 1. 浏览主页定位

`HLTV` 页面首先是一个“浏览主页”。

- 每次刷新抓到的比赛，默认都视为“素材缓存”而不是正式沉淀。
- 页面职责是：快速浏览、筛选、挑选比赛，再决定哪些值得沉淀到正式库。
- 因此它不应再承担过多说明性 dashboard 或伪过滤占位，而应以比赛内容密度和筛选效率优先。

### 2. 暂存库（Staging Library）

HLTV 抓到的数据先进入本地 `暂存库`。

#### 暂存库职责

- 保存抓到的比赛基础资料，供后续人工筛选。
- 支持长期累积素材，不再自动定期清空。
- 清理方式改为手动：可以选择按条件清理，或执行一键清空。

#### 暂存库默认缓存内容

每场比赛至少缓存：

- match 基础信息：`matchId`、URL、队伍、比分、赛事、比赛时间、BO 类型
- map 级信息：
  - 地图名称 / slug
  - 每张地图的胜负结果
  - 地图比分（如果能抓到）
- 战队基础信息：队伍名、队标、HLTV team URL
- 后续可继续补的轻量信息：event URL、ranking snapshot、featured 标签等

#### 暂存库的特性

- 默认允许重复刷新同一场比赛，并做 upsert 更新
- 允许数据不完整，只要足够支持“浏览和筛选”
- 不要求默认抓取选手详情、完整 team/player detail、或 demo 文件

### 3. 永久库（Permanent Library）

用户在暂存库中手动挑选比赛，才将比赛转存到 `永久库`。

#### 永久库职责

- 只存“被确认值得保留”的比赛
- 作为后续长期检索、内容整理、Playbook 关联、demo 分析沉淀的正式来源

#### 永久库默认增强内容

比赛进入永久库后，需要补抓更丰富的数据，例如：

- team detail
- player detail / lineup snapshot
- 更完整的 map-level metadata
- 赛事上下文信息

但默认 **不自动下载 demo**。

也就是说：

- `进入永久库` ≠ `自动下载 demo`
- demo 下载仍然是用户手动触发动作

### 4. 双库之间的动作模型

核心动作应明确分离：

- `刷新 HLTV`：写入暂存库
- `加入永久库`：从暂存库复制/提升到永久库
- `下载 demo`：对指定比赛手动执行
- `清空暂存库`：人工确认后执行
- `从永久库删除`：单独动作，不受暂存库清空影响

### 5. 当前实现与目标差距

当前代码并没有双库：

- `HLTV refresh` 后会直接写入本地 cache
- `本地资料库` 直接读取这批 cache 数据
- 没有独立 staging 表 / permanent 表
- 也没有“从暂存库批准进入永久库”的动作

所以 HLTV 方向的第一优先级不是继续堆更多筛选，而是先把数据层边界改正确。

## 二、Playbook 方向

### 1. Playbook 的定位

`Playbook` 是项目里的第二条内容沉淀主线，不只是附属笔记页。

它要承载的内容包括：

- 战术
- 投掷物
- 职业选手信息
- 用户自己新建的知识条目

它既是知识库，也是和 demo 分析结果联动的沉淀面板。

### 2. 与 Demo 解析的联动

Playbook 不应完全靠手工录入，而应和 demo 解析结果联动。

目标能力包括：

- 在 demo 解析结果中直接查看投掷物
- 把某个投掷物直接加入“收藏 / Playbook”
- 保存其轨迹信息：从哪里丢，到哪里爆/落
- 保存它与地图位置的对应关系

后续这部分最好形成“从解析结果一键生成 Playbook 条目”的流程，而不是要求用户手工二次录入所有字段。

### 3. 自定义标注素材

Playbook 条目应支持用户补充自己的观察素材，例如：

- 游戏截图
- 标注后的站位图
- 瞄点图
- 补充说明文字

也就是说，Playbook 条目既要支持结构化字段，也要支持图文补充。

### 4. 与职业信息的关系

Playbook 不只记录“我自己的投掷物”，也应支持整理职业内容，例如：

- 某职业选手的常见点位
- 某战队在某地图的默认或特定战术
- 从职业比赛中提取出来的投掷物与站位案例

这意味着 Playbook 模型最好能支持：

- 关联比赛
- 关联地图
- 关联选手 / 战队
- 关联 demo 片段 / 回合 / 时间点

### 5. 当前实现与目标差距

当前项目还没有真正的 Playbook 系统。

现阶段最接近的只有：

- 回放/解析能力
- 未来可能复用的实体库（战队/选手）
- 回合 note 的雏形

但还没有：

- Playbook schema
- Playbook 页面
- 投掷物收藏链路
- 轨迹沉淀模型
- 图片附件与标注模型

所以 Playbook 需要单独作为一条新主线，而不能继续塞进现在的 HLTV 页里零散实现。

## 三、与 Obsidian 的绑定方向

### 1. 目标

项目里的 Playbook 内容，需要能和本地 Obsidian 中的 Playbook Markdown 文件体系关联。

目标不是简单“导出一个文件”，而是：

- 在本项目中创建/编辑的 Playbook 内容
- 能够映射到 Obsidian 中可阅读、可继续整理的 Markdown 页面

### 2. 推荐边界

建议把“项目内结构化数据”和“Obsidian 展示/沉淀页面”分层：

- 项目内保存结构化数据、图片索引、关联关系
- Obsidian 负责 Markdown 呈现、人工整理、二次扩写和知识串联

也就是说，项目内数据是 source of truth，Obsidian 是可读可编辑的外部知识视图。

### 3. 后续需要明确的问题

这条线后续要进一步明确：

- Obsidian Playbook 的目录规范
- 一个 Playbook 条目对应一个 md，还是一个主题聚合页
- 图片资源放在项目目录、Obsidian 附件目录，还是双向引用
- 编辑冲突以哪边为准
- 是单向导出，还是支持双向绑定

在当前阶段，建议先以“项目内生成/更新 Obsidian Markdown 页面”的单向同步为第一版目标，不一开始追求完全双向编辑。

## 四、当前推荐的实现顺序

### 第一阶段：先把 HLTV 数据边界做正确

1. 把当前“refresh 直接写 cache”改成“refresh 写暂存库”
2. 新增“加入永久库”动作与 permanent schema
3. 本地资料库分成“暂存库 / 永久库”或提供明确切换
4. 补齐 map-level 缓存，而不只停留在比赛标题和 demo 文件名推断

### 第二阶段：让永久库成为稳定入口

1. 永久库补抓 team / player / match detail
2. 下载 demo 维持手动触发
3. 让永久库更顺滑地进入 demo 分析、回放和实体筛选

### 第三阶段：启动 Playbook 主线

1. 定义 Playbook 数据模型
2. 打通“从 demo 投掷物结果加入收藏”
3. 支持截图 / 瞄点 / 站位标注
4. 设计 Obsidian Markdown 同步出口

## 六、结论

当前项目最需要先修正的，不是继续微调 HLTV 页文案或补更多伪筛选，而是把 `HLTV 素材暂存` 和 `正式长期沉淀` 这两个层级拆开。

在这之后，再把永久库作为 demo 分析与未来 Playbook 的稳定上游。Playbook 则应作为独立主线设计，不混在 HLTV 页里零散生长。
